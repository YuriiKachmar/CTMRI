# Оптимізація програми: пам'ять, швидкодія, обсяг (читання/запис бази)

Статус: **робочий документ**. Сюди записуємо, що вже оптимізовано, як це вимірювати і за якими правилами додавати нові функції, щоб програма не «гальмувала» і не впиралась у квоти Firebase.

## 1. Для чого це
Програма — один HTML-файл + база Firebase Firestore (проєкт `ctmri-1`). Три «вузькі місця»:
1. **Читання бази** (гроші/квота): безкоштовно 50 000 документів на добу; кожен документ у відповіді запиту = 1 читання; порожня відповідь = 1 читання.
2. **Пам'ять і швидкодія пристрою**: великі масиви в JavaScript (звіт за 4 роки), довгі таблиці, SVG-графіки.
3. **Обсяг** бази й файлу: розмір документів, кількість полів, розмір `index.html`.

## 2. Ліміти Firebase (безкоштовний тариф Spark; перевірити актуальні на сторінці Firebase Pricing)
| Ресурс | Безкоштовно на добу / місяць |
|---|---|

| Записи | 20 000 / добу |

| Вихідний трафік | 10 ГіБ / місяць |
Квота читань скидається опівночі за тихоокеанським часом (≈ 10:00–11:00 за Києвом). Тариф Blaze має ті самі безкоштовні межі, понад них — копійки (≈ 0,06 $ за 100 тис. читань); для спокою — бюджетне сповіщення (напр. 1 $).
Також: **правила Firestore, які викликають `get()`/`exists()`, теж дають читання** (перевірка ролі в кожному запиті) — це видно як різницю між лічильником програми і Firebase Console.

## 3. Як вимірювати
- **Firebase Console → Firestore → Usage:** загальні читання/записи всіх користувачів за добу (єдине точне джерело; включає читання від правил). Власного лічильника в програмі немає: він бачив би лише один браузер, тож був неточним (прибрано 23.11.2026 за рішенням власника).
- **Лічильник у звіті:** під заголовком управлінського звіту — скільки документів прочитано останнім завантаженням і чи це «лише зміни».
- **Браузер (F12):** вкладка Performance/Memory — пам'ять сторінки; Network — розмір відповідей. Не вірити тестам у Chromium щодо Safari/iPhone: перевіряти на реальному пристрої.

## 6. Правила для нових функцій (чек-ліст перед додаванням)
1. **Скільки читань на одну дію?** Порахувати: (документів у відповіді) × (скільки разів за добу). Якщо > ≈ 500 на дію — потрібен кеш, ліміт або агрегат.
2. **Запит із `limit`** там, де потрібен лише початок списку (пошук, «останні N»).
3. **Не читати «все за період» повторно.** Дані, що не змінюються (минулі роки, `createdAt` пацієнтів), кешувати в IndexedDB; змінні — дочитувати за `updatedAt`.
4. **Слухачі `onSnapshot`** лише там, де потрібне «живе» оновлення (Журнал за сьогодні, календар чергувань). Зупиняти, коли вікно закрите; не вішати слухач на великий період.
5. **Нові поля документа** — короткі імена/значення; не дублювати великі об'єкти (знімки послуг уже містять назву/ціну/тривалість — не додавати зайвого).
6. **Кожен запис документа ставить `updatedAt`** (потрібно кешам). Видалення — через журнал `audit_log` (з `before.records`) або «м'яке» (статус), інакше кеш не побачить видалення до «перечитати все».
7. **Пам'ять:** не тримати в JS одночасно більше ≈ 50–60 тис. об'єктів-записів; великі розрахунки — один прохід, без повторних `filter` у циклах по днях.
8. **Перевірка:** мікротест на імітованій базі (повне читання → 0 без змін → мало після змін) + реальна цифра у Firebase Usage до і після.
9. **Записати** в розділ 5 цього файлу, що зроблено і який ефект.

## 7. Відомі «гарячі» місця й ідеї на майбуття
- **Перше повне відкриття управлінського звіту** (≈ 70 тис. читань): варіанти — (а) тариф Blaze з бюджетним сповіщенням; (б) читати лише потрібні роки за вкладкою (сезонність/тенденції — лише коли відкрито); (в) **денні підсумки** — окрема колекція агрегатів за день, яку оновлює програма при записі візиту (найекономніше, але потребує узгодження структури й міграції).
- **Правила Firestore (`get()` ролі)** додають читання на кожен запит — зменшити можна лише кількістю запитів; роль у токені (custom claims) — окрема велика зміна.
- **Видалення поза візитом** (без `audit_log`) кеш не побачить до «перечитати все» (звіт) / до добового повного оновлення (довідники).
- **Safari у приватному режимі**: IndexedDB може бути недоступний → щоразу повне читання.
- **Розмір `index.html`:** один файл росте; якщо стане повільно завантажуватись — розділити на модулі й стиснення (окреме рішення власника).
- **Журнал змін `audit_log`** росте безкінечно — потрібна політика очищення/архівації (рішення власника).

## 9. Коли інший користувач бачить зміни (синхронізація між пристроями)
| Дані | Коли з'являються на іншому пристрої |
|---|---|
| Візити/записи в Журналі (поточний вибраний період) | **одразу** (слухач `onSnapshot`, секунди) |
| Календар чергувань | одразу (`onSnapshot`) |
| Картка відкритого пацієнта (його візити) | одразу, поки картка відкрита |
| Довідники (нова послуга, пільга, установа, працівник тощо) | **лише після повторного входу/перезавантаження сторінки** (`loadDirs` викликається при вході); власні зміни видно одразу |
| Управлінський звіт | після «Оновити дані» (дочитує лише зміни) |
| Інші звіти | при кожному формуванні звіту (читають із бази) |
| Пошук пацієнтів | на момент пошуку |
